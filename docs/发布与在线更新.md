# 发布与在线更新

2026-11-14。目标仓库：[qmqsu/folio](https://github.com/qmqsu/folio)，站点：<https://qmqsu.github.io/folio/>。

**这里描述的是自动化及启用步骤，不表示已经部署、已经发布或已经完成实机验收。** 缺少生产签名密钥、公开源码白名单、许可核查或人工验收时，脚本必须失败，不能生成“示例成功”或临时生产公钥。

## 1. 构建与适用范围

- ESP-IDF `v6.1` / `6.1.0`，固定提交 `fff9895c82d744c7237be8847347bdd1b07c6643`，递归子模块使用该提交记录的版本。工具链按该提交的工具清单安装，Xtensa GCC `esp-15.2.0_20251204`。
- 应用及板级组件由仓库精确提交固定；[组件锁文件](<../dependencies.lock>)不得在发布中更新。发布配置使用独立临时配置，不读取本机调试配置；[release override](<../.github/sdkconfig.release>)明确关闭 USB debug，打包再检查编译配置及镜像调试标记。
- 仅限 **RDP-G01-W、ESP32-S3、16 MiB、Zbit ZB25VQ128 / JEDEC 0x5E4018** 的已核实板型。现有 Flash/PSRAM **120 MHz 实验配置**原样保留；不是通用 ESP32-S3 固件。稳定提升必须包含实际温升稳定性、物理屏幕与 Flash 身份证据。
- 应用必须不超过 `3145728` 字节；校验实际 ESP 镜像校验和/SHA256、app descriptor、芯片、版本、构建序号、实际二进制分区表及初始 otadata。
- 本机 IDF 曾有仅修复日志目录创建的 host Python 小补丁，导致 `v6.1-dirty`；这种本机镜像不会被发布脚本当成干净发布。CI 先创建构建目录，使用未修改的固定 IDF。

## 2. 工作流与权限

| 入口 | 实际行为 |
| --- | --- |
| main 普通 push | [Checks](<../.github/workflows/check.yml>)运行主机回归、发布安全回归、网站测试/类型检查/构建；通过后发布当前 main 的静态站，并保留已有固件及通道。 |
| pull request | 同样检查；不部署、不读取签名密钥、不使用 `pull_request_target`。 |
| `v<version>` 标签 | [Release](<../.github/workflows/release.yml>)构建一次、准备源码/许可/离线材料，经受保护 `release-signing` 环境批准后签名，发布 **preview**。正式版本号也先进入 preview。 |
| 人工 stable 提升 | [Promotion](<../.github/workflows/promote.yml>)下载已经发布且签名的离线包，**不重建**；核对已提交的实机验收记录，经 `release-stable` 环境批准后签 stable 通道。 |

所有工作流默认只有 `contents: read`。只有共用 [Pages publisher](<../.github/workflows/publish.yml>)部署 job 拥有 `contents: write`、`pages: write`、`id-token: write`，用于 Release、Pages 和状态 CAS。该 job 无生产签名 secret。签名 secret 只在两个受保护环境的签名步骤传入；脚本还通过 GitHub API 检查 required reviewers 和分支/标签限制，不能只靠环境名称假装受保护。

Actions 全部固定完整提交 SHA。Node `22.23.4`、pnpm `11.28.5`、Python `3.13.3`、cryptography `48.0.1`；网站依赖由锁文件固定。没有读取或上传生产私钥的调试命令。

## 3. 序号与签名协议

构建和清单同源版本序号：

```text
major * 100000000 + minor * 1000000 + patch * 1000 + stage
minor <= 99，patch <= 999，总数 <= uint32
-dev      → 0
-dev.N    → N，1..499
-rc.N     → 500+N，N=1..498
正式版    → 999
0.8.32-dev → 8032000；0.8.32-dev.1 → 8032001；0.8.32 → 8032999
```

不允许前导零或无编号 `-rc`。首发允许基线 `8032000`；其后新版本必须大于所有历史发布序号，重复版本/重复序号/旧 workflow 晚完成都拒绝。stable 提升只允许同一已发布正式版本的原始序号和镜像，且严格高于之前 stable；不会为了提升通道重新编译或伪造新序号。设备自身仍拒绝同序号 OTA。

清单最大 `4096` 字节：

```text
envelope = {key_id:"folio-release-2026-2", payload:base64(UTF8 canonical JSON bytes),
            signature:base64(ECDSA-P256 SHA256 raw r||s, 64 bytes)}
```

canonical JSON 采用 UTF-8、不转义非 ASCII、字典键排序、无多余空白。签名覆盖原始 payload 字节；不是对重新序列化结果验签，不是 ASN.1 DER 签名。共同字段严格限定为 schema=1、kind、project=Folio、chip=esp32s3、hardware=RDP-G01-W、固定 layout、channel、version、sequence，以及可选不超过512 UTF-8字节 notes。

- OTA：`image={url,size,sha256}`，路径固定 `https://qmqsu.github.io/folio/firmware/<version>/folio.bin`。
- USB：`flash_size=16777216`，只有4个 `parts`，每项 `{url,offset,size,sha256}`，顺序/偏移固定为 `0`、`0x8000`、`0x10000`、`0x910000`。
- 默认 USB/OTA 不包含 merged、erase-all、NVS、字体资源或 storage 写入。字体本版只提供独立说明及完整可读许可；不能作为默认下载后自动安装项。
- 公开信任锚为 [生产公钥](<../keys/firmware-release-public.pem>)，不是从待安装的网络清单动态信任新公钥。
- 额外的 `materials.json` 是所有离线材料的 SHA256 映射，`materials.sig` 为同一生产公钥对应的 raw P-256/SHA256 64字节签名，覆盖源码、许可证、provenance 和两种清单；这不是扩展 OTA/USB payload 字段。

固定通道 URL：

```text
https://qmqsu.github.io/folio/channels/preview.json
https://qmqsu.github.io/folio/channels/stable.json
https://qmqsu.github.io/folio/channels/preview-usb.json
https://qmqsu.github.io/folio/channels/stable-usb.json
```

404 表示尚未发布，不能回退到未签名清单。版本目录不可变；其中 `ota.json` / `usb.json` 保留最初 preview 签名，stable 另有通道签名，引用同一镜像。

## 4. 不先更新指针、并发与失败恢复

共用部署 job 使用全仓库统一 `folio-pages-publication` concurrency，`cancel-in-progress: false`。锁覆盖“读取当前状态 → 重新校验序号 → 准备完整站点 → 部署 → 实际URL校验 → 状态CAS”，而不是只锁上传动作。

`folio-pages-state` 分支上的 `.github/pages-state.json` 是权威状态：记录 generation 与当前 `release-state.tar.gz` 的 SHA256。每次从公开 Pages 取回快照，严格比对该 SHA256，再检查所有签名和镜像。只收到404、网络错误或快照不一致时不能当成空历史重新发布。

完整新 Pages artifact 同时包含静态站、新旧全部固件、通道清单、验收记录和恢复快照；GitHub Pages 一次切换，**不会先写指针再上传镜像**。普通网站更新也必须经过同一流程，不得直接用空网站覆盖发布目录。版本材料先发布到不可变 GitHub Release，才暴露固件指针。至少上一版本始终保留；当前实现不自动删除任何版本。固件历史达到400 MiB展开量时拒绝继续，而不是静默删除旧版；将来如增加保留策略，必须先保证旧版仍有明确永久下载地址和已有指针不破损。

失败情况：

- 编译/签名/验收/组装/Release上传失败：原站点保持不动。
- Pages部署失败：不更新权威状态，旧站点仍由Pages的原部署提供。
- 新Pages已切换、后续状态CAS或CDN核验失败：新站点不会被回滚；下一次自动发布因快照与权威状态不一致而**停止**。维护者必须核对已部署快照、run记录和签名，之后人工修复权威状态，不能删除状态或将generation改回0。
- Release已创建而Pages未部署：同标签重跑不会覆盖现有Release。在main运行[Recover工作流](<../.github/workflows/recover-release.yml>)，选择原tag：只下载原已签名字节、不读取密钥、不重建、不修改Release，并通过同一序号/签名/原子部署门禁。若版本已上线或历史已有更新则拒绝。禁止删tag重建、`--clobber`或拿新签名字节替换旧资产。
- GitHub concurrency只保留一个等待job，旧等待任务可能被平台丢弃；这是跳过过时任务，不是允许回退。最后真正执行的任务仍重新核验sequence。

## 5. 源码、隐私与许可证门禁

[发布打包器](<../tools/release_bundle.py>)不调用原有开发打包器的打包入口。只复用它的分区/字体校验函数；不自动递归归档整工作区，不复制本机配置、私有证据或历史照片。

发布前维护者必须审查并提交 `.github/release-source-files.txt`，一行一个**精确相对文件名**，不支持glob、不支持目录、不跟随源码symlink、不提供扫描fallback。所有 main/components/licenses 文件必须明确覆盖；白名单每个文件按Git blob逐字节匹配目标tag commit。缺项、旧构建、未提交改动、路径穿越、绝对路径、备份/照片/私有目录、本机配置、密钥/token都拒绝。生产公钥有唯一受控 PEM 例外，私钥没有例外。

还必须由维护者完成实际核查后提交 `.github/release-legal.json`：

```json
{
  "schema": 1,
  "publisher": "qmqsu",
  "repository": "https://github.com/qmqsu/folio",
  "project_license": "MIT",
  "third_party_reviewed": false,
  "corresponding_source_reviewed": false,
  "font_licenses_reviewed": false
}
```

上面故意是**未批准、不能发布**的记录。不能为了CI通过把false机械改true。MIT只覆盖自研部分，不替代第三方、SDK、LGPL或字体OFL义务。

[SDK许可采集器](<../tools/release_licenses.py>)从实际 build_component_info 收集链接组件、ESP-IDF根许可/COPYRIGHT、固定子模块commit以及实际编译器 share/licenses 下的原文，强制包含 GCC Runtime Library Exception/newlib；输出 `sdk-notices/` 和 `license-inventory.json`。这是有明确边界的材料清单，**不冒充完整SPDX/SBOM或自动法律意见**。无独立许可文件的SDK组件明确列出根许可fallback供人工复核。

离线包包含对应源码、全部项目许可、字体NOTICE/来源及OFL、SDK/工具链notice、来源commit/文件hash、四段镜像、清单和材料签名。`relink.tar.gz` 附保留符号与重定位的静态库、链接脚本、strip-debug后的ELF、发布配置及重建说明；不带原始本机build日志/CMakeCache。CI使用编译prefix maps，材料发现 `/Users/` 或私钥/token即失败。仍须人工确认 LGPL 替换/重链接所需材料与对应源码完整，不以有一个ELF代替法律审查。

## 6. 一次性 GitHub 配置（需仓库管理员执行）

此代理不代替管理员写远端。以下仅为明确操作步骤，未执行不能说已部署。

1. 先审查公开导出、MIT/第三方材料、生产公钥和白名单。将代码推到公开 `qmqsu/folio` 的 main。不要推私钥、历史私有资料或本机配置。
2. Settings → Pages → Build and deployment → Source 选 **GitHub Actions**。仓库Actions默认权限保持 read；工作流在实际部署job提升最低必要权限。允许使用已固定SHA的官方actions。
3. Settings → Environments 创建 `release-signing`、`release-stable`、`github-pages`。前两个启用 **Required reviewers**，单人维护者选择 `qmqsu`（不要启用Prevent self-review导致自己无法批准）；设置分支/标签策略：`release-signing`仅匹配标签 `v*`，`release-stable`仅main，`github-pages`允许main及`v*`。禁用管理员随意绕过门禁；有第二名维护者时启用Prevent self-review。程序会检查签名环境确实存在reviewers和branch policy。
4. 仅在前两个环境分别添加 `FOLIO_SIGNING_KEY_PEM`，内容为既有生产P-256私钥PEM。不要创建同名仓库/组织级secret，不要把私钥回显、写入CI文件或加入artifact。私钥必须匹配仓库公钥；此工作流不会生成key。使用管理员本机 `gh secret set --repo qmqsu/folio --env release-signing FOLIO_SIGNING_KEY_PEM < /受控私钥路径`，stable环境同理。
5. 为main启用审查/必需checks，重点保护workflow、发布脚本、公钥、白名单、legal记录与验收记录。对`v*`标签启用ruleset限制创建者，禁止更新和删除标签；避免可修改workflow的未审查tag接触签名环境。
6. **本轮lead已完成状态分支初始化，无需用户再操作。** `folio-pages-state` 的初始化提交为 `1ca29d539ae376547928f24e1aaaf3b1cb63a75e`，仅包含 `schema:1,generation:0,snapshot_sha256:null` 的状态；这不表示Pages已配置或上线。下面命令只供未来新仓库首次初始化参考，当前仓库不要重跑（会写远端）：

```sh
repo=qmqsu/folio
main_sha=$(gh api "repos/$repo/git/ref/heads/main" --jq '.object.sha')
gh api --method POST "repos/$repo/git/refs" -f ref=refs/heads/folio-pages-state -f sha="$main_sha"
initial=$(printf '%s' '{"schema":1,"generation":0,"snapshot_sha256":null}' | base64 | tr -d '\n')
gh api --method PUT "repos/$repo/contents/.github/pages-state.json" \
  -f branch=folio-pages-state -f message='Initialize empty atomic Pages state' -f content="$initial"
```

该分支只记很小的状态JSON，不将二进制提交到Git。禁止强制重置/删除，保留Actions内容写入能力。若分支已存在或线上已有快照，不重跑初始化；按失败恢复章节核查。

7. 配置完成后在Actions重新运行main的Checks，确认实际站点能打开、空通道返回404而非虚假成功。核对一次公开snapshot和状态分支SHA一致。之后普通push可更新站点，推版本标签可触发preview发布（仍要环境批准）。

## 7. 可执行 stable 实机验收

取得preview包、验签后由人实际安装验证，记录绑定**同一版本、源码commit、应用SHA256**。记录位于 `.github/release-acceptance/<version>.json`，提交到main并审查后，运行Promotion选择已经存在的正式版本tag。

必需字段：`schema:1`、`version`、`source_commit`（40hex）、`app_sha256`（64hex）、`hardware:RDP-G01-W`、固定`layout`、`approved:true`、真实GitHub `reviewer`、UTC `tested_at`。`checks`必须精确包括以下11项；每项均有 `passed:true` 及16～1024字符的可核查 `evidence`：

- device_identity：确切板型及设备记录（不要公开原始唯一身份/账户资料）；
- flash_identity：Zbit0x5E4018、16MiB与实际分区；
- usb_four_parts：四段USB、完整备份、明确操作许可；
- ota_signed_upgrade：同一候选的真实签名OTA升级；
- ota_reject_invalid：坏签名/错镜像/回退输入拒绝；
- boot_rollback：启动确认/失败回滚；
- nvs_storage_preserved：NVS/storage未被默认安装覆盖；
- reading_smoke：真实阅读/重启恢复；
- physical_display：真实物理屏幕，不以帧缓存截图代替；
- thermal_stability：当前120MHz BOM温度/持续运行验证；
- font_fallback：未安装或无效字体资源时回退、不写storage。

脚本拒绝缺项、false、错hash/commit、`TODO/pending/not tested/fixture/example/待测/未测/示例`证据文本；也拒绝-dev/-rc stable。格式校验不能证明人真的测过，所以受保护环境中的真实审阅是第二道独立门禁。仓库不附带假成功验收记录。

## 8. 本机验证命令与边界

```sh
FOLIO_PYTHON="$HOME/.espressif/python_env/idf6.1_py3.13_env/bin/python" \
  sh tools/tests/run_release_tests.sh

# 只验证已有清单，不签名、不联网、不接触私钥：
"$FOLIO_PYTHON" tools/release_manifest.py /待验证清单.json \
  --public-key keys/firmware-release-public.pem

# 按实际build metadata采集许可供人复核，不代表批准发布：
"$FOLIO_PYTHON" tools/release_licenses.py --root "$PWD" \
  --description /实际build/project_description.json --output /全新审查目录
```

测试密钥只在临时目录/内存中即时生成，明确标注TEST FIXTURE；做cryptography与OpenSSL双向真实ECDSA验证，不替换公钥或生产secret。回归涵盖版本/序号、混版、Debug、尺寸、路径/私有文件、签名篡改、人工门禁、重复发布、旧任务与历史保留。

主机测试通过不表示GitHub环境已设置、Pages部署成功、真实烧录成功或实机显示/温度/OTA已验收。发布脚本不连接设备；没有签名key或验收记录时保持未发布状态。
